# Establishing the Standard Process for Tech Documentation
#### Background/ Problem Defined<br>
I noticed how powerful documentation is. I felt a strong need for establishing a process to document a project process specifically relating to the technical steps. As I worked on multiple projects and got more experience in the company, I saw that there were types of problems that showed certain patterns or were raised repeatedly. 
<br>
> ex) 
> - We were repeatedly reported with similar types of inquiries in certain areas by stakeholders.
> - We faced the same problems repeatedly.
> - We had to go through time-consuming steps whenever debugging certain issues.

The common denominator between those issues is that the problem occurs repeatedly and we spend time to address the same type of issues again and again each time it's raised. I thought technical documentation could alleviate the root cause of the problems and prevent it early on.     
<br>
The most important types of technical documentation needed to be generated per report were a data dictionary, a report manual, and an edit history summary. I believe the absence of these types of information documented and the absence of spreading awareness of such information to stakeholders did not establish a standardized understanding of the subject matter internally and externally which ended up resulting in the same issue reported repeatedly. Therefore, I suggested introducing an official documentation step as part of the standard product delivery package.
<br><br>

#### Solution Provided<br>
<details>
  <summary><b><i>1. Data Dictionary</i></b> (Click to see details)</summary>
<br>
It provides the detailed information about data included in a report. It contains the field names, definitions of the fields, and an example value per field.
<br><br>
One of the primary reasons behind the data dictionary development was that end-users didn't have a good understanding of the data they were referring to in reports than I expected. Also, we received a lot of inquiries from them asking for clarification about the logic of calculated fields and complex metrics. I believe it was likely due to the absence of a data dictionary and it could have clarified many questions on their end if the supporting documentation for data was provided to refer to. 
<br><br>
__________ understanding around data was not only limited to end-users.
It was not only limited to end-users. I was surprised to discover that the absence of a data dictionary to refer to impacted the developer end as well across teams. I discovered it when I built a data dictionary for major datasources. I got peer reviews from colleagues from different teams to make sure that my understanding of the definitions of fields was correct, but I learned that there was an ambiguous or different understanding among developers when there were many similar fields available in the data. 
<br>
It was very critical to our product design since it led them to use different fields when they were referring to the same concept of the product. Even when they had the right concept of the product, they actually used incorrect/ different fields in the code.
<br><br>
End-user들은 자신이 보고있는 데이터에대한 이해도가 생각보다 낮았는데, 그들에게 official data dictionary가 제공되지않아 그들이 우리에게 데이터에대해 자주 문의를 했었다. 그리고 또 내가 알게된 사실이 developers사이에서도 비슷한 테이터가 많을 경우에 이해하고있는 데이터의 의미가 조금씩 다르다는것도 알게되었다.
그리하여 각 리포트마다 포함된 데이터에관한 Data dictionary를 end-user에게 제공하였다.
